# Backlog after 2.3.0

| Item | Status | Why |
|---|---|---|
| A2: Chrome-parity shim (`requestIdleCallback`, `scheduler.postTask`) | Not done | A0 found no page error from a missing API: the Analytics panel failed only because the first click on an inactive window never reached the page (fixed by A1). WebKit's own `RequestIdleCallbackEnabled` exists (private `WKPreferences _setEnabled:forFeature:`), but its status on macOS 27.0.1 is "Testable" and Safari ships it off, so turning it on, or shimming it in the page world, would change the code path Zoho tests against Safari. Add it only when a page is shown to fail without it. |
| A3: smooth animations in Low Power Mode | macOS limit | With Low Power Mode on, WebKit runs `requestAnimationFrame` (and CSS animations) at 30 fps; Chrome keeps 60. Checked on macOS 27.0.1: none of the 601 `WKPreferences._features` controls it (searched Throttl, LowPower, 60FPS, RenderingUpdate, Power, Timer; `PreferPageRenderingUpdatesNear60FPSEnabled` is about high-refresh displays and already on), and the only selector is the testing-only `WKWebView _setThrottleStateForTesting:`. Animations still finish on time (parity: 31 fps, ~310 ms). Turning Low Power Mode off in System Settings › Battery gives 60 fps. |
| B2: web notifications (Cliq, Mail, CRM reminders) | Verified missing; not implemented | Reproduced on macOS 27.0.1 in a bare WKWebView (https page, real click): `Notification.permission` is `default`, `requestPermission()` resolves `denied` at once, `new Notification()` fires `error`. The SDK has no public WebKit notification API. Tried, with no effect: the UI-delegate method `_webView:requestNotificationPermissionForSecurityOrigin:decisionHandler:` (never called), and a data-store `_delegate` answering `notificationPermissionsForWebsiteDataStore:` (asked, but the page still sees `default`) and `websiteDataStore:showNotification:` (never called), with and without the `BuiltInNotificationsEnabled` feature. The remaining route is WebKit's private C API (`WKContextGetNotificationManager` + `WKNotificationManagerSetProvider` with a versioned callback struct, permission through `WKPageSetPageUIClient`, which would replace WKWebView's own UI client). A struct layout cannot be checked like a selector, so a macOS update could crash the app; that breaks the "guarded, fail closed" rule. Safari's own path goes through `webpushd`, which needs Apple entitlements. Workaround: Zoho's own Mac apps (Cliq, Mail) or Zoho's mobile apps for alerts. |
| B6: two-finger swipe-back inside wide Zoho grids | Not reproduced; dropped | On the user's Mac "Swipe between pages" is off (`AppleEnableSwipeNavigateWithScrolls` = 0; three-finger horizontal swipes switch full-screen apps), and AppKit reports `NSEvent.isSwipeTrackingFromScrollEventsEnabled` = false, so WKWebView never starts a back swipe however the grid scrolls. `setAllowsBackForwardNavigationGestures(true)` stays. If "Swipe between pages" is ever turned on and a grid edge navigates back, ignore the gesture while an editable element has focus (`EDITOR_HOOK` already reports focus changes). |

Still open from the 2.0 backlog after 2.3.1: Log360 Cloud SA/SG/CN (waits on Zoho; re-checked 2026-10-30), web notifications (B2, no safe route), and the manual passes with real accounts (checklist in `docs/TESTING.md`). Done in 2.3.1 with the owner's go-ahead: closing the window hides it (S1), VoiceOver announces the sheet's inline error (U2), the address icon sits inside the field (D7). Custom SAML providers (U3): not needed, no client uses one.
